上下文工程

随着任务进行，请求中包含的token总量会越来越多，但模型可以处理的token量不能无限制增长，最终会受到模型上下文窗口的限制。

随着任务轮数的增长，工具调用请求、工具调用执行结果不断增多，很容易突破模型上下文窗口限制，API 直接报错，几十轮的工作当场清零。

造成的后果

1.token费用暴增。

2.注意力被稀释，关键信息丢失。

上下文工程的目标

管理发送给模型的上下文，决定窗口中放什么，不放什么，让窗口里的每个 token 都在为当前决策服务。

一次请求的token总量= system prompt + 工具 Schema + 全部历史 + 本轮请求，

内容 处理原则
system prompt 不能动
最近几轮消息 保留
更早的消息 进行压缩，它们的价值已经提炼到了后续的决策中

上下文处理的原则

缓存机制的原理是前缀匹配，要尽可能保证前缀相同。

1.system prompt不能有动态信息。

2.中间消息不能修改，如果修改，后面的消息全部作废。

3.压缩的收益和代价一起算。压缩的代价有：缓存作废、历史信息损耗、压缩本身的开销。

压缩

压缩策略伪代码

当历史消息的大小超过阈值的时候，保留system prompt、最近消息，把中间的消息进行压缩。

三部分划分的细节：

1.assistant tool_call 和 tool result一定要同时存在，不能切开，否则历史里出现了没有配对的消息，API会拒绝接收。

2.压缩本身就是一次大模型调用。有token开销、有延迟、有信息损耗。

3.压缩中间部分的提示词要明确保留什么，最重要的是保留未完成的事项。压缩的质量决定压缩后Agent的表现。

持久化

每条消息追加写入一个jsonl文件。

优点：

1.好恢复，直接读入当作历史消息数组就恢复了。

2.好读，保留了所有历史，方便调试。

3.好分析，使用文本工具就能分析统计。

4.实现会话分叉，把前几行消息复制到另一个新会话。

跨会话记忆

压缩和持久化针对单次会话，跨会话记忆同样是把prompt写入文件，请求时假如上下文中。

两个坑：

1.恢复会话后重新执行已经做过的操作，历史或摘要里没有明确记录”已完成”，模型就会再做一遍。

2.记忆和现实冲突，记忆是线索，不是事实，用之前验证，冲突时信当下。
