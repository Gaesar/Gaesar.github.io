# Agent测评

Agent 是概率系统，单次运行是抽样，不是结论。同一个任务跑两遍，轮数和路径都不一样。

测评是业余Agent开发和职业Agent开发的分界线。

业余的开发流程是"改一下，试一下，感觉行了"；职业的流程是"改一下，跑一遍评测集，通过率从 6/10 变成 9/10，合并"。

## 测评集

评测集就是一组固定的任务，每个任务配一个程序能自动判定对错的标准。

### 构建测评集的经验

- 任务来自真实失败，最好的评测任务是"它曾经栽过跟头的活"，凭空设计的任务往往测不到真实的弱点。
- 难度要有梯度，有过有挂的评测集才能感知变化。
- 初始状态必须可验证，每个任务在 Agent 动手前应该"至少挂一个测试"，动手后"全部通过"。两头都要程序确认，否则你可能在评一个根本没坏的项目。
- 数量不用大，10 个精心挑选的任务足够指导日常开发，评测集是开发工具，先要快和准。

## 测评方式

- 程序判分，最可靠，优先用。
- LLM-as-judge，另一个Agent当裁判，给没有唯一答案的产出打分。但裁判自己也是概率模型，要抽查它判得准不准。
- 人工评审，用来校准前两个，处理的是用户满不满意的问题。

## 可信测评

普通能力测评, 只关心任务能不能做完，看最终答案对错。

Agent 可信测评，不仅看任务结果，重点监控 Agent 执行过程，每一步工具调用、异常处理、有没有撒谎、越权、幻觉、是否完成的是真正的任务。即使任务成功，但过程存在大量幻觉，依然判定为不可信。

例如：修改代码bug的任务中，Agent通过作弊，直接修改了测试文件，或者直接对着测试样例硬编码，使得结果看起来通过了，但这样的结果是不可信的。

## 测评程序的骨架

> 分为三步：运行任务、判分、汇总

```
results = []
for task in 评测集:
    work = 把任务复制到临时工作目录(task)     # 每次评测用干净副本，别弄脏原件
    try:
        运行Agent("修复 {work} 里的 bug", 独立会话)
    except Agent崩了:
        pass                                # 崩溃计为失败，评测继续
    integrity = 比较前后文件哈希()           # 测试和配置不能被改
    check = runner执行可见测试和独立测试()   # 判分：不信汇报，亲自跑
    results.append({任务: task, 状态, 修改文件, 轮数, 耗时, 会话id})

打印汇总表(results)                          # 通过率 x/10 + 每个任务一行
写入JSON文件(results)                        # 存档，改动前后对比全靠它
```

每个任务要满足：

- 干净副本，评测要可重复，上一次的残局不能影响这一次。
- 崩溃不中断，一个任务把整场评测炸掉，你连其他任务的数据都拿不到。
- 独立会话，每个失败任务都有完整轨迹可供检查

## 测评代码分析

### 输入文件

### 核心步骤

 ```
 1.为本次测评生成一个run_id，创建/eval_work/{run_id}，本次测评的工作目录
 2.读取manifest测评清单，取出{任务名称: 任务配置}
 3.将当前测试任务复制到工作目录中，记录工作前任务目录下文件的hash值，记录在字典中
 4.运行测试文件，如果测试已经通过，或者测试超时，直接返回，确实存在失败，继续下一步
 5.设置工具的工作目录，每次实际执行工具前校验，超出工作目录范围，直接报错
 6.{任务名称: 任务配置}注入Agent的message中，作为user信息
 
 7.Agent Loop执行任务，返回最终汇报的执行结果
 
 8.记录工作后任务目录的hash值，记录在字典中
 9.比较前后两个字典，统计出被修改了的文件名称，和manifest中允许修改的文件做比较
 10.再次运行测试文件，验证模型的任务完成情况
 分为以下几种情况：
 	1. PASSED：允许的源码修改通过了可见测试和独立测试
 	2. FAILED：独立测试仍然失败
 	3. TAMPERED：修改了清单以外的文件
 	4. TIMEOUT：测试执行超时
 	5. ERROR：运行过程出错
 用一个results数组收集每一个任务的完成情况
 11.统计完成情况，并将结果汇总的文件/eval_results下的.json文件中
 ```

### Agent Loop外的额外操作

> 限制工作目录、限制可操作文件，不能只在提示词中限制，还要落实到代码中，在执行工具前校验, 不符合拒绝执行。

1.限制工作目录：

- 提示词层面限制。

- 创建本次测评的工作目录，把测试任务放到工作目录中。
- 执行工具前校验将要操作的目录是否是工作目录，不是直接报错不执行。

2.不允许修改指定文件外的文件：

- 提示词限制。
- 记录测试前任务文件的hash值，任务完成后，记录测试后任务文件的hash值，从而别到。
- 也可以给工具配置可操作文件，操作了可操作之外的文件，直接报错不执行。

3.两头确认，开始任务前，执行独立测试，确保存在错误，完成任务后，执行独立测试，验证是否解决错误。

4.测试文件有两类

- 可见测试， Agent执行过程中可以看到的，执行的测试文件。 
-  独立测试，Agent执行过程中看不到的，不能执行的测试文件，避免Agent围绕测试文件中的样例硬编码。

## trace分析

通过率告诉你"挂了几个"，不告诉你"为什么挂"。

失败任务的检查流程是，打开它的 JSONL 从头读：它 grep 了什么、读了哪个文件、在哪一轮开始跑偏。

按角色顺序找，找第一个和事实分叉的位置。

比如工具已经返回“文件不存在”，下一轮却原样读取同一路径，这是错误信息没有推动策略变化。

测试明确说边界包含 100，模型却去改测试，这是权限与目标对齐问题。

工具调用根本没发生就超时了，则还没到代码推理那一层。

失败通常聚类，不是十个任务十种死法，而是同一个坑绊倒了三个任务。

**评测的价值就在这个循环里：跑分 → 检查轨迹 → 改一处 → 重跑**

## 回归分析

修改后常常会出现，一个任务改好了，另外两个任务挂了，没有评测集，这种倒退要等用户投诉才被发现；有评测集，重跑一遍就马上发现。

职业的改法永远是：改动之前先跑一遍基线，改动之后再跑一遍基线对比。只有测量规则没变、结果确实变好，才有资格说改好了。

一次改动只对应一个假设，然后重跑同一批任务。否则你同时改 prompt、工具描述、超时和模型参数，即使通过率上升，也不知道是哪一个变化起作用。

> 改动流程

```
跑分 → 给失败分类 → 找共同的第一处分叉 → 改一处 → 重跑
```

当结果再次变化时，新的 trace 应该能回答旧问题：之前那类失败是否真的消失，有没有换一种形式出现在别处。这才叫回归分析。
