# 检索

## 大模型应用中检索的场景

1.聊天机器人从知识库中检索相关知识。

2.编码Agent从代码文件中检索代码片段。

## 大模型应用中检索的两种方案

### 语义检索

检索相关的内容，不是精确匹配，是语义上的匹配。

### 语法检索

使用grep命令精确匹配。

## RAG流程

RAG属于语义检索，把检索的结果加入prompt让模型回答。

分为两个阶段：

离线阶段构建索引，加载文档，切分文档，将每一个文档块转为向量存储到向量库中。

在线阶段查询向量库，将用户问题转为向量，在向量库中做相似度匹配，取出最相近的top-k个文档，加入prompt让模型回答。

> 检索流程

```
# 离线：建索引
docs   = 加载文档()
chunks = 切分(docs, 每块约几百字)               # ① Chunking
vectors = [embedding模型(c) for c in chunks]   # ② 向量化
向量库.存入(chunks, vectors)                    # ③ 存储

# 在线：查询
qv   = embedding模型(用户问题)
hits = 向量库.相似度top_k(qv)                   # ④ 召回
answer = 调用模型(f"根据以下资料回答：{hits}\n"  # ⑤ 生成
                  f"问题：{用户问题}")
```

注意事项：

1.切分的太大，语义不准确，精度下降；切分太小，一个部分可能被分为两块。

一般按照文档的标题、段落做切分，相邻两块保留一部分重叠，防止边界信息丢失。

对于代码，按照函数、类做切分。

总原则：宁愿切的大也不能切的太碎。

2.Embedding选型，选型看三件事：目标语言效果（查 MTEB/C-MTEB 评测榜）、向量维度（影响存储和检索速度）、能否私有部署。

3.向量库，按量级选工具：几千个向量，numpy 数组暴力算余弦就够；数十万级用 FAISS（单机索引库）；要增删改查、元数据过滤、生产运维，再上 Milvus / Qdrant 这类专门数据库。

4.召回优化

- **混合检索**：词法 + 语义各召回一批再合并。
- **rerank**：先粗召回 top-50，再用精排模型选出 top-5。
- **query 改写**：让 LLM 把口语问题改写成更适合检索的形式（"那个报错咋回事" → "NullPointerException 原因"）。

5.生成

把召回块拼进 prompt 时带上来源（文件名、段落号），让答案可溯源。

top_k 不是越多越好，召回 20 块全塞进去，预算爆炸且信噪比骤降，常见起点 3-5 块。

## RAG评估

调 RAG 先看检索质量（该找到的找到了吗）再看生成质量（找到了答得对吗）。

绝大多数"RAG 效果差"是检索质量的问题，不是生成质量的问题。

检索质量可以脱离模型单独测：拿 20 个问题人工标注该命中的文档，算命中率。系统化的评测框架（如 RAGAS）也是这个思路的工程化。

相似度分数只用来排序，不同向量模型的分数分布完全不同，不能跨模型比较。

## grep

主流的coding agent没有用rag而是使用grep

原因：

1.代码检索需要精确匹配，使用语义检索反而会带来噪音。

2.代码随时都会修改，rag需要离线建立索引，每次修改都重新建立不太现实。

3.Agent理解用户后发出的grep命令，本身就包含语义了。

4.Agent有循环，可以多次尝试。

使用rag的情况：

1.查询很难精确匹配上，例如用户向客服的提问。

2.知识库几乎不变，不需要频繁建立索引。

3.要求一次命中，没有重试的机会。



## 二者结合Agentic RAG

把检索作为工具，让Agent决定使用什么检索。

优点是：能重试，能组合多种检索方式

缺点是：重试次数多，导致延迟和成本高。
